## 1. Threat Model & Security Scope

PatchProof executes code modifications generated by autonomous AI agents and untrusted third parties. The security architecture assumes that:
1. **The patch is potentially hostile:** A patch may attempt path traversal, symlink escapes, code injection, denial-of-service, or data exfiltration.
2. **The test suite is untrusted:** Tests executed post-patch may run arbitrary Python code with intent to compromise host infrastructure.
3. **The host environment contains sensitive credentials:** Host environment variables, cloud configs (`~/.aws`, `~/.config`), and SSH keys exist on the host OS.
4. **Git worktrees are NOT security sandboxes:** A worktree only provides branch isolation; any code run in a worktree runs with full developer OS privileges.

### 2.1. Docker Command Construction & Injection Defense
- **Implementation:** [`src/patchproof/sandbox/docker_cli.py`](src/patchproof/sandbox/docker_cli.py)
- **Subprocess Execution:** All commands are built as strictly typed string sequences (`list[str]`) and passed to `subprocess.Popen` with `shell=False` and `close_fds=True`.
- **Pre-execution Security Validation:** `verify_command_security()` verifies that every command includes mandatory security flags (`--network=none`, `--user=10001:10001`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, `--read-only`). Commands missing any flag are rejected before execution.

### 2.2. Environment Sanitization & Credential Hygiene
- **Implementation:** `EnvironmentSanitizer` in [`src/patchproof/sandbox/docker_cli.py`](src/patchproof/sandbox/docker_cli.py)
- **Denylist Patterns:** Rejects any host environment variable matching patterns such as `TOKEN`, `KEY`, `SECRET`, `PASSWORD`, `AUTH`, `CREDENTIAL`, `AWS`, `GITHUB`, `GH_`, `DOCKER`, `SSH`.
- **Explicit Allowlist:** Containers receive only strictly vetted safe variables (`PATH`, `LANG`, `LC_ALL`, `PYTHONUNBUFFERED`, `PYTHONDONTWRITEBYTECODE`, `PYTHONPATH`, `CI`, `TERM`, `PYTEST_*`). Host environments are never inherited.

### 2.3. Filesystem Mount Strategy & Host Immutability
- **Symmetrical Staging Isolation:** The original host repository is NEVER mounted or modified by container execution. Instead, both baseline and patched executions run inside separate, ephemeral staging workspaces created in system tempdir (`patchproof-staging-base-*` and `patchproof-staging-patch-*`) via `safe_copy_repository()`.
- **Target Workspace Mounting:** Staging directories are mounted directly at container `/workspace` so test runners locate all repository source code without discrepancy.
- **Root Filesystem Protection:** Container root filesystem is mounted with `--read-only`. Temporary file writes are accommodated via tmpfs at `/tmp` (64MB) and within the ephemeral staging mount at `/workspace`.
- **Guaranteed Staging Destruction:** In the `finally` block of `ComparativeRunner.run()`, `safe_cleanup_staging()` validates that each staging path is inside `tempfile.gettempdir()`, has the prefix `patchproof-staging-`, and is not a root or shallow path before recursively deleting it. Any test caches or temporary files generated during tests are completely destroyed upon completion.
- **`.git` Credential Masking:** A 1KB empty tmpfs mount with mode `000` is mounted over `/workspace/.git` inside the container, preventing tests from accessing local Git configuration, commit history, or stored credentials even if `.git` were present.

### 2.4. Network Isolation Boundary
- **Flag Enforced:** `--network none`
- **Validation:** Both domain models (`SecurityPolicy.network_mode == NetworkMode.NONE`) and CLI builders strictly forbid network connectivity. Tests cannot make outbound connections to download secondary payloads or exfiltrate environment data.

### 2.5. Resource Limits & Denial-of-Service Defense
- **CPU Quota:** Enforced via `--cpus` (default: 1.0, maximum: 4.0).
- **Memory Limit:** Enforced via `--memory` and `--memory-swap` set to equal values to disable swap escape (default: 1024MB, maximum: 4096MB).
- **PID Limit:** Enforced via `--pids-limit` (default: 128, maximum: 512), preventing fork bombs.
- **Tmpfs Quota:** Bounded via `--tmpfs /workspace:size=256m` and `/tmp:size=64m`.
- **Host-Monitored Timeout:** A host-side supervisor monitors container execution and kills unresponsive containers after the configured timeout (default: 15.0s, maximum: 300.0s).

### 2.6. Container Ownership, Sweeping, and Lifecycle Cleanup
- **Ownership Labels:** Every container is labeled with `patchproof.managed=true`, a unique `patchproof.execution_id`, and a creation timestamp.
- **Orphan Sweeper:** `OrphanSweeper` inspects lingering containers and removes ONLY stopped containers older than the grace period matching `patchproof.managed=true`. Broad cleanup commands (`docker system prune`) are strictly prohibited.
- **Guaranteed Cleanup:** `ContainerRunner.run()` wraps execution in `try ... finally` blocks, ensuring that even if execution fails or is interrupted via SIGINT (`Ctrl+C`), the container is terminated and removed.

### 2.7. Symlink & Path Traversal Mitigations
- **Patch Application Guard:** [`src/patchproof/core/applier.py`](src/patchproof/core/applier.py) resolves targets against the workspace base, rejects parent traversal (`..`), rejects drive-root escapes, and strictly rejects targeting or modifying symbolic links (`target_candidate.is_symlink()`).
- **Repository Cloning Guard:** [`src/patchproof/sandbox/comparative.py`](src/patchproof/sandbox/comparative.py) pre-scans all files with `followlinks=False` before staging copy. Any symlink whose resolved path escapes `src_root` raises `SandboxSecurityError`.
- **Staging Cleanup Invariants:** Ephemeral staging cleanup verifies three boundary checks before issuing `rmtree`: must be within `tempfile.gettempdir()`, must match `patchproof-staging-*`, and must not be a filesystem root.

### 2.8. Output Buffering & Memory Protection
- **Bounded Stream Capture:** [`StreamCapture`](src/patchproof/sandbox/runner.py) caps container stdout and stderr at 4MB (`DEFAULT_MAX_OUTPUT_BYTES = 4 * 1024 * 1024` bytes), truncating excess output with a diagnostic banner to prevent host memory exhaustion from runaway container log generation.

### 2.9. Fail-Closed CLI Contract
- Under no circumstances does PatchProof fall back to executing untrusted code on the developer's host machine.
- If Docker is missing, stopped, or configured in Windows container mode, PatchProof immediately aborts with `ExitCode.INFRASTRUCTURE_FAILURE` (4).
- Exit code `0` (`ACCEPTED`) is returned if and only if the patch verified clean with 0 regressions, all tests passed, and test results were complete.
